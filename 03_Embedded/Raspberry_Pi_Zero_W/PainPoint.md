**대상 시스템**: Raspberry Pi Zero W + OV5647 (SunFounder Camera Rev 1.3) / Raspberry Pi OS Trixie  
**적용 범위**: 촬영 단계에 한정 (전송·AI 처리 단계는 제외)

## 0. 분석 전제

이후 모든 근거는 아래 사양에서 도출됩니다.

### 하드웨어 사양

| 항목 | 값 |
|---|---|
| SoC | BCM2835, ARM1176JZF-S 싱글코어 1GHz (ARMv6) |
| RAM | 512 MB LPDDR2 |
| 무선 | 802.11n 2.4GHz 단독 |
| RTC | **없음** (Jetson 시각 동기화로 보완 — 내2 참조) |
| 센서 | OV5647, 1/4인치 CMOS, 5MP, 화소 크기 1.4µm |
| 초점 | **고정 초점** (수동 조절만 가능) |
| 셔터 방식 | 롤링 셔터 |
| 화각 | 수평 약 53.5°, 수직 약 41.4° |
| CSI 커넥터 | 22핀 미니 (일반 Pi의 15핀과 비호환) |

### 실측 센서 모드

`rpicam-hello --list-cameras` 출력:

```
0 : ov5647 [2592x1944 10-bit GBRG]
    Modes: 'SGBRG10_CSI2P' : 640x480   [62.50 fps - (16, 0)/2560x1920 crop]
                             1296x972  [46.34 fps - (0, 0)/2592x1944 crop]
                             1920x1080 [32.81 fps - (348, 434)/1928x1080 crop]
                             2592x1944 [15.63 fps - (0, 0)/2592x1944 crop]
```

### 파생 상수

| 항목 | 값 | 산출 |
|---|---|---|
| 픽셀당 각해상도 | **0.0413 °/px** | 53.5° ÷ 1296px |
| 시간당 용량 (3Mbps) | **1.35 GB** | 3,000,000 ÷ 8 ÷ 1024² × 3600 |
| 2시간 총 프레임 (15fps) | **108,000장** | 15 × 7200 |
| 녹화 중 소비전력 | 약 1.3~1.8 W | 250~350mA @ 5V |

## 2. 내부 요인

시스템 자체의 사양·구조에서 발생하는 문제입니다.

---

### 내1. 연산 자원 부족 — 온디바이스 처리 불가

**문제**
촬영 중 프레임을 분석·선별·보정하는 어떤 작업도 실시간으로 수행할 수 없습니다.

**근거**
- ARMv6 싱글코어 1GHz. 멀티코어 병렬 처리 불가
- RAM 512MB. 프레임 버퍼링 여력 제한
- H.264 인코딩은 VideoCore IV 하드웨어가 처리하므로 CPU 부담이 없으나, **프레임 데이터를 CPU로 끌어오는 순간** 상황이 달라짐
- 1296×972 YUV420 프레임 1장 = 약 1.9MB. 15fps면 초당 28MB를 CPU가 읽어야 함
- `picamera2` import만으로 ARMv6에서 5~10초 소요 (numpy + libcamera 바인딩)

**영향**: 아키텍처 전체를 규정. Zero W는 "기록 전담" 역할로 고정됨
**가역성**: 해당 없음 (설계 제약)

---

### 내2. RTC 부재 — 타임스탬프 신뢰성

**문제**
Zero W에는 배터리 백업 실시간 시계가 없습니다. 전원이 끊긴 뒤 외부 시각원 없이 부팅하면 시스템 시각이 부정확해집니다.

**근거**
- Zero W에는 배터리 백업 실시간 시계가 탑재되지 않음
- `fake-hwclock`이 마지막 종료 시각을 복원하지만, 전원이 꺼져 있던 실제 경과 시간은 반영하지 못함
- 외부 시각원에 접근할 수 없는 위치에서 부팅하면 동기화 실패
- 확인 명령: `timedatectl show -p NTPSynchronized --value`

**영향**
일기 생성의 근간이 시간 순서이므로, 시각이 어긋나면 **결과물 자체가 성립하지 않습니다.** "오후 3시의 공원"이 "새벽 2시"로 기록되면 AI가 작성하는 서술 전체가 오염됩니다.

---

#### 채택 해결책 — Jetson 시각 동기화

Jetson Orin Nano가 상시 전원으로 가동되므로, 이를 **로컬 시각 기준점(NTP 서버)** 으로 사용합니다.

```
Jetson Orin Nano  (상시 전원 · 시각 기준)
        │  LAN 또는 USB 가젯
        ▼
   Pi Zero W      (부팅 시 동기화 → 산책 → 복귀 시 재동기화)
```

**이점**

| 항목 | 효과 |
|---|---|
| 추가 하드웨어 | **불필요** (기존 구성만으로 해결) |
| 인터넷 의존성 | **제거** — 폐쇄망에서도 동작 |
| 공용 NTP 실패 리스크 | 제거 |
| 전송 파이프라인과의 결합 | 동일 경로 재사용 (USB 가젯 시 특히 유리) |

**정확도의 전제 조건**

"한 번 설정하면 계속 유지된다"는 **Jetson이 자체적으로 정확한 시각원을 갖고 있을 때만** 성립합니다.

| Jetson 네트워크 상태 | 시각 정확도 |
|---|---|
| 인터넷 NTP 연결 | 지속 교정. 오차 무시 가능 |
| 폐쇄망 (오프라인) | 수정 발진자 표류 누적 |

수정 발진자 오차는 통상 ±20~50 ppm입니다.

| 오차 | 하루 | 한 달 | 1년 |
|---|---|---|---|
| 20 ppm | 약 1.7초 | 약 52초 | 약 10분 |
| 50 ppm | 약 4.3초 | 약 2.2분 | 약 26분 |

일기 용도에서 월 1~2분 오차는 실질적 문제가 되지 않습니다. 다만 폐쇄망 운용 시 **분기 단위 재교정**을 권장합니다.

---

#### 잔여 위험 — 기지국 밖 재부팅

이 방식은 **Zero W가 Jetson에 접근 가능할 때만** 시각을 교정합니다. 따라서 다음 경우가 남습니다.

| 시나리오 | 시각 정확성 | 발생 가능성 |
|---|---|---|
| 기지국에서 부팅 → 재부팅 없이 산책 | ✅ 정확 | 정상 운용 |
| 산책 중 언더볼티지 재부팅 (내5) | ❌ 부정확 | 실재 |
| 배터리 교체로 인한 재부팅 | ❌ 부정확 | 장시간 촬영 시 |
| 기지국 외 장소에서 최초 부팅 | ❌ 부정확 | 운용 방식에 따라 |

**즉 내2는 단독으로는 발생하지 않고, 내5(전원 불안정)와 결합될 때만 문제가 됩니다.** 두 항목이 종속 관계로 묶입니다.

---

#### 잔여 위험의 사후 보정

야외 재부팅이 발생하더라도, **Zero W가 전원을 유지한 채 기지국으로 복귀하면 시각을 사후 복원할 수 있습니다.**

**원리**: 벽시계(`CLOCK_REALTIME`)는 틀려도 단조 시계(`CLOCK_MONOTONIC`)는 정확합니다. 단조 시계는 부팅 이후 경과 시간만 세므로 절대 시각이 틀려도 영향받지 않습니다.

**보정 절차**

1. 세션 시작 시 벽시계와 단조 시계를 **함께** 기록
2. 기지국 복귀 후 Jetson과 재동기화하는 시점에 두 값을 다시 기록
3. 오프셋 계산:

```
실제_세션_시작 = 교정된_현재_시각 − (현재_단조시계 − 세션시작_단조시계)
```

4. 이 오프셋을 세션 메타데이터에 기록하고, 후단에서 전체 타임스탬프에 일괄 적용

**성립 조건**: 세션 종료부터 재동기화까지 **Zero W가 전원을 유지**해야 합니다. 중간에 전원이 끊기면 단조 시계가 초기화되어 복원이 불가능합니다.

**메타데이터 예시**

```json
{
  "clock_source": "jetson_ntp",
  "clock_synced_at_start": false,
  "boot_id": "3f2a...",
  "session_start_realtime": "2026-07-27T14:30:22+09:00",
  "session_start_monotonic": 1847.3,
  "resync_realtime": "2026-07-27T17:12:05+09:00",
  "resync_monotonic": 11450.8,
  "estimated_offset_sec": -3612.4
}
```

`clock_synced_at_start`가 `false`이고 `estimated_offset_sec`이 존재하면, 후단은 해당 세션의 모든 타임스탬프를 오프셋만큼 이동시킵니다.

#### 대안 비교

| 항목 | Jetson 동기화 | DS3231 RTC 모듈 |
|---|---|---|
| 비용 | **0원** | 약 3,000원 |
| 배선 | 불필요 | I2C 4핀 |
| 기지국 부팅 | ✅ | ✅ |
| 야외 재부팅 | ❌ (사후 보정 가능) | ✅ |
| 정확도 | Jetson에 종속 | ±2 ppm (TCXO 내장) |
| 장기 표류 | 폐쇄망 시 누적 | 연 1분 이내 |

**판단**: Jetson 동기화를 **주 해결책**으로 채택합니다. 비용이 없고 기존 전송 경로를 재사용할 수 있으며, 정상 운용 시나리오를 완전히 커버합니다. DS3231은 야외 재부팅 빈도가 실측으로 확인될 경우에 한해 **보험 성격으로 추가**합니다.

**가역성**: **부분 가역** — 단조 시계 앵커링으로 사후 보정 가능. 단, 재동기화 전 전원 손실 시 비가역
**우선순위 변동**: 3위 → 6위 (해결 구조 확보로 강등)

### 내3. 센서 모드별 화각 차이

**문제**
해상도 설정에 따라 센서의 사용 영역이 달라집니다. 1080p 선택 시 화각이 크게 좁아집니다.

**근거**
실측 crop 값 기준 계산:

| 모드 | crop 영역 | 가로 사용률 | 세로 사용률 | 면적 |
|---|---|---|---|---|
| 1296×972 | 2592×1944 | 100% | 100% | 100% |
| 1920×1080 | 1928×1080 | 74.4% | 55.6% | **41.4%** |

수평 화각 환산: 53.5° → 약 41°. **1.34배 확대(줌인)된 것과 동일**

**영향**
산책 일기는 주변 맥락 정보가 핵심 소재입니다. 화각이 좁아지면 담기는 정보량이 직접 감소합니다.

**가역성**: **비가역** (촬영되지 않은 영역은 복원 불가)
**현재 상태**: `--mode 1296:972` 적용으로 해결됨

### 내4. 고정 초점

**문제**
피사체 거리에 따라 초점을 맞출 수 없습니다. 근거리 피사체(꽃, 간판, 표지판)가 흐리게 기록됩니다.

**근거**
- OV5647 모듈은 고정 초점 방식. 렌즈 나사를 수동으로 돌리는 것 외에 제어 수단 없음
- `rpicam-vid --help`의 오토포커스 관련 옵션(`--autofocus-mode`, `--lens-position`)은 Camera Module 3 전용
- 공장 출하 초점은 대략 1m~무한대. 근접 촬영 시 해상력 급감
- 수동으로 근거리에 맞추면 원경이 흐려지는 트레이드오프 발생

**영향**: 근접 피사체 프레임의 활용도 저하
**가역성**: **비가역** (초점 이탈은 후처리로 복원 불가)

### 내5. 전원 불안정

**문제**
배터리 구동 시 언더볼티지 리부팅, 보조배터리 자동 차단, 방전으로 촬영이 중단됩니다.

**근거**
- 녹화 중 소비전류 250~350mA. WiFi 활성 시 추가 80mA 이상, 송신 시 순간 스파이크
- 다수의 보조배터리가 저전류 부하를 "기기 미연결"로 판단해 출력을 자동 차단. Zero W는 이 임계값 근처에서 동작
- 전압 강하 시 SoC가 클럭을 낮추거나 리부팅. 확인: `vcgencmd get_throttled` (정상값 `0x0`)
- 케이블 저항으로 인한 전압 강하도 요인. 얇은 케이블일수록 심함

**영향**: 촬영 중단 시점 이후 전체 손실
**가역성**: **비가역**

---

### 내6. CSI 리본 케이블 접촉 불량

**문제**
보행 진동으로 커넥터 접촉이 불안정해지면, 그 시점부터 촬영이 실패합니다.

**근거**
- Zero W의 22핀 미니 CSI 커넥터는 물리적으로 작고 래치 강도가 약함
- 웨어러블 사용은 지속적인 진동과 케이블 굽힘을 수반
- 접촉 불량은 **프로세스가 살아있는 상태에서 프레임 공급만 중단**되는 형태로 나타나는 경우가 있어, 단순 프로세스 감시로는 탐지되지 않음

**영향**: 촬영 실패 (내8과 동일 증상)
**가역성**: **비가역**

---

### 내7. 관측 불가 — 헤드리스 운용

**문제**
촬영이 정상 진행 중인지 현장에서 확인할 방법이 없습니다.

**근거**
- 디스플레이·상태 LED·부저 등 피드백 장치 없음
- SSH 접속은 네트워크 필요. 야외에서는 불가
- 결과 확인은 귀가 후에만 가능

**영향**
**단일 항목 중 손실 규모 최대.** 2시간 촬영이 실패해도 현장에서 인지할 수 없고, 산책은 재현 불가능합니다. 화질 관련 문제 전체를 합친 것보다 손실이 큽니다.

**가역성**: **비가역**

---

### 내8. 소프트웨어 실패 모드

**문제**
프로세스 크래시 또는 무응답 상태로 촬영이 중단됩니다.

**근거**
두 가지 실패 양상이 구분됩니다.

| 유형 | 증상 | 탐지 난이도 |
|---|---|---|
| 명시적 크래시 | 프로세스 종료 | 낮음 (systemd `Restart=`로 대응) |
| **무응답(silent failure)** | **프로세스는 생존, 파일 크기 정지** | **높음** |

후자는 내6(케이블 접촉 불량)이나 카메라 초기화 실패 시 발생하며, 프로세스 감시만으로는 잡히지 않습니다. **파일 크기 증가 여부를 별도로 감시해야 탐지 가능합니다.**

**영향**: 촬영 실패
**가역성**: **비가역**

---

### 내9. 저장 공간 및 파일 무결성

**문제**
저장 공간 고갈 또는 전원 손실 시점의 파일 손상이 발생합니다.

**근거**
- 3Mbps 기준 시간당 1.35GB 소비. 32GB SD 카드 기준 약 20시간
- 공간 고갈 시 파일시스템 손상 위험
- `.h264` 원시 스트림은 인덱스가 없어 잘려도 그 지점까지 디코딩 가능
- 반면 MP4는 인덱스(moov)를 파일 종료 시 기록하므로, **녹화 도중 전원이 끊기면 파일 전체가 재생 불가**

**영향**: 손상 시점 이후 손실 (세그먼트 분할 시 마지막 세그먼트로 제한)
**가역성**: **비가역**
**현재 상태**: 세그먼트 분할(`--segment 300000`) + `--flush` 적용으로 완화됨

## 3. 외부 요인

촬영 환경에서 발생하며, 통제할 수 없고 적응만 가능한 문제입니다.

---

### 외1. 급격한 조도 변화 ★ 최다 발생

**문제**
햇빛과 그늘을 오갈 때 자동 노출이 재수렴하는 동안, 프레임이 과다 노출되거나 과소 노출됩니다.

**근거**
- 산책 경로는 나무 그늘, 건물 그림자, 지하도, 실내를 반복적으로 통과
- 실외 직사광과 그늘의 조도 차이는 수십 배에 이름 (대략 100,000 lux vs 1,000~10,000 lux)
- libcamera AGC의 수렴 시간은 통상 0.5~2초. 15fps 기준 **8~30 프레임이 손상**
- 하이라이트가 클리핑되면(픽셀값 포화) 해당 영역의 정보가 물리적으로 존재하지 않아 **후보정 불가**

**영향 범위의 특수성**
다른 화질 문제와 달리 **프레임 단위가 아니라 구간 단위로 손실**됩니다. 이 때문에 "많이 찍어서 좋은 것을 고르는" 전략이 통하지 않습니다. 구간 전체가 균일하게 망가지기 때문입니다.

**가역성**: **비가역** (클리핑 영역), 부분 가역 (과소 노출은 일부 복원 가능)

---

### 외2. 보행 진동 → 모션 블러

**문제**
한 프레임의 노출 시간 동안 카메라가 이동하면 해당 프레임이 흐려집니다.

**근거**
지배 변수는 흔들림의 크기가 아니라 **셔터 속도**입니다.

블러량 = 각속도 × 셔터시간 ÷ 0.0413 °/px

보행 중 가슴 마운트 각속도를 20°/s로 가정할 때:

| 셔터 속도 | 블러량 | 판정 |
|---|---|---|
| 2 ms | 약 1 px | 문제 없음 |
| 8 ms | 약 4 px | 허용 가능 |
| 20 ms | 약 10 px | 글자 판독 불가 |
| 33 ms (1/30초) | 약 16 px | 사용 불가 |

셔터 속도는 조도에 따라 자동 결정되므로, **밝은 야외에서는 거의 문제가 없고 그늘·흐린 날·해질녘에 급격히 악화**됩니다. 즉 외2는 실질적으로 외1의 종속 변수입니다.

**중요**: 프레임 간 위치가 튀는 "흔들림"과 한 프레임 내부가 번지는 "블러"는 다른 문제입니다. 최종 소비자가 프레임 단위로 읽는 VLM이므로 **전자는 무해하고 후자만 유해합니다.**

**가역성**: 부분 가역 — 다른 프레임으로 대체 가능한 경우에 한함 (아래 조건 참조)

**모수 전략의 유효 조건**
"많이 찍어 선명한 것을 고른다"는 방식은 **프레임 간 선명도 분산이 존재할 때만** 작동합니다. 조도가 낮아 전 구간 셔터가 20ms로 유지되면 150장이 균일하게 흐리므로 선택의 여지가 없습니다. 따라서 셔터 확보가 선행 조건이며, 모수 확보는 2차 방어선입니다.

---

### 외3. 롤링 셔터 왜곡

**문제**
빠른 좌우 움직임에서 화면이 기울어지거나 흔들리는 젤로(jello) 현상이 발생합니다.

**근거**
- OV5647은 롤링 셔터 방식. 센서를 위에서 아래로 순차 스캔
- 스캔 중 카메라가 움직이면 상단과 하단의 촬영 시점이 달라져 형상이 왜곡됨
- 왜곡 정도는 센서 읽기 속도에 반비례
- 1296×972 모드는 최대 46.34fps로 읽기가 빠름. 2592×1944 모드(15.63fps)보다 왜곡이 현저히 적음

**영향**: 정지 프레임에서는 인지하기 어려움. 동영상 재생 시 두드러짐
**가역성**: 부분 가역 (후처리 난이도 높음)
**현재 상태**: 1296×972 모드 사용으로 완화됨

### 외4. 역광

**문제**
하늘이나 광원을 향할 때 전경 피사체가 실루엣으로 처리됩니다.

**근거**
- 측광 모드가 화면 평균 또는 중앙 가중치로 노출을 결정
- 배경이 밝으면 전경을 어둡게 만드는 방향으로 노출이 결정됨
- 보행 중 카메라 방향이 계속 변하므로 발생 시점을 예측할 수 없음
- OV5647 세대 센서는 다이내믹 레인지가 좁아 명부와 암부를 동시에 담기 어려움

**가역성**: 부분 가역 (암부 정보가 남아 있으면 일부 복원 가능)

### 외5. 피사체 거리 분포

**문제**
산책 중 피사체 거리가 수십 cm에서 무한대까지 분포하나, 고정 초점으로는 일부만 선명하게 담깁니다.

**근거**
- 내4(고정 초점)와 외부 환경의 결합으로 발생
- 원경 위주로 초점을 맞추면 근접 피사체(꽃, 간판, 안내판)가 흐려짐
- 일기 소재로서의 가치는 오히려 근접 피사체가 높은 경우가 많음

**가역성**: **비가역**

### 외6. 렌즈 오염

**문제**
비, 먼지, 지문, 김서림으로 전체 프레임의 화질이 균일하게 저하됩니다.

**근거**
- 야외 웨어러블 환경에서 렌즈 노출이 불가피
- 착탈 과정에서 지문 접촉 가능성
- 온도차에 의한 결로
- **모든 프레임이 동일하게 영향받으므로 프레임 선별 전략이 무력화됨**

**가역성**: **비가역**
**대응**: 소프트웨어로 해결 불가. 물리적 관리(렌즈 후드, 발수 코팅, 촬영 전 점검)만 가능

### 외7. 장면 중복성 — 낮은 정보 밀도

**문제**
촬영 분량의 대부분이 정보 가치가 없는 반복 장면(인도, 아스팔트, 담벼락)입니다.

**근거**
- 2시간 촬영 × 15fps = **108,000 프레임**
- 일기 소재로 활용 가능한 프레임은 수십 장 수준으로 추정
- 신호 대 잡음비 약 **0.05~0.1%**
- 보행 속도가 일정하므로 연속 프레임 간 변화량이 극히 작음

**영향**
촬영 단계에는 무해하나, 전송 시간과 후단 처리 비용을 직접 증가시킵니다.

**가역성**: **가역** (후단 선별로 해결)

### 외8. 제3자 사생활

**문제**
공공장소 촬영 시 타인의 얼굴과 차량 번호판이 불가피하게 기록됩니다.

**근거**

- Zero W에서 실시간 익명화 처리는 불가능 (내1)
- 개인 일기 용도라 하더라도 원본 데이터의 보관·전송 정책 수립이 필요

**가역성**: **가역** (후단 익명화 가능)
**전제 조건**: 후단 익명화를 파이프라인에 포함시키는 설계

## 4. 내부 × 외부 상호작용

대부분의 페인 포인트는 단일 요인이 아니라 **내부 제약과 외부 조건의 결합**에서 발생합니다.

| 외부 조건 | 내부 제약 | 결과 |
|---|---|---|
| 조도 변화 (외1) | 좁은 다이내믹 레인지 | 하이라이트 클리핑 |
| 보행 진동 (외2) | 조도 종속 셔터 속도 | 저조도 구간 모션 블러 |
| 보행 진동 (외2) | 약한 CSI 커넥터 (내6) | 촬영 무응답 실패 |
| 근접 피사체 (외5) | 고정 초점 (내4) | 초점 이탈 |
| 장시간 야외 (외7) | 전원 한계 (내5) | 촬영 중단 |
| **야외 재부팅** | **RTC 부재 (내2) × 전원 불안정 (내5)** | **타임스탬프 오류 (사후 보정 가능)** |
| 촬영 실패 | 관측 불가 (내7) | 실패를 인지하지 못함 |

**해석**
외부 요인은 통제할 수 없으므로, **대응은 전부 내부 제약을 완화하는 방향**으로 이루어져야 합니다.

특히 주목할 두 행이 있습니다.

- **야외 재부팅 행**: Jetson 시각 동기화 채택 이후, 내2는 더 이상 단독으로 발생하지 않습니다. 내5(전원 불안정)가 유발 조건이 되므로, **내5를 잡으면 내2도 함께 해결**됩니다. 대응 자원을 내5에 집중하는 근거입니다.
- **마지막 행**: 관측 불가(내7)는 다른 모든 실패의 **손실 규모를 증폭시키는 요인**입니다.

## 5. 우선순위 판단

### 판단 기준

우선순위 = 발생 빈도 × 손실 규모 ÷ 대응 난이도

**손실 규모**를 세 단계로 구분합니다.

| 등급 | 정의 |
|---|---|
| **전체** | 해당 산책 전체를 잃음 |
| **구간** | 수 초~수 분 단위 손실 |
| **프레임** | 개별 프레임 손실 (대체 가능) |

### 종합 순위

| 순위 | 항목 | 구분 | 빈도 | 손실 규모 | 가역성 |
|---|---|---|---|---|---|
| 1 | 내7 관측 불가 | 내부 | — | **전체** | 비가역 |
| 2 | 내8 무응답 실패 | 내부 | 낮음 | **전체** | 비가역 |
| 3 | 내5 전원 불안정 | 내부 | 중간 | **전체** | 비가역 |
| 4 | 내6 케이블 접촉 | 내부 | 낮음 | **전체** | 비가역 |
| 5 | 외1 조도 변화 | 외부 | **매우 높음** | 구간 | 비가역 |
| 6 | 내2 시각 오류 | 내부 | 낮음 (내5 종속) | **전체** | **부분 가역** |
| 7 | 외2 모션 블러 | 외부 | 높음 | 프레임 | 부분 가역 |
| 8 | 외6 렌즈 오염 | 외부 | 낮음 | **전체** | 비가역 |
| 9 | 외4 역광 | 외부 | 중간 | 프레임 | 부분 가역 |
| 10 | 외5 초점 이탈 | 복합 | 중간 | 프레임 | 비가역 |
| 11 | 외7 중복성 | 외부 | 상시 | 없음 | 가역 |
| 12 | 외8 사생활 | 외부 | 상시 | 없음 | 가역 |

> **개정 이력**: 내2(시각 오류)는 Jetson 시각 동기화 채택 이전 3위였습니다. 해결 구조 확보로 발생 빈도가 "중간 → 낮음(내5 종속)", 가역성이 "비가역 → 부분 가역"으로 변경되어 6위로 조정되었습니다.

### 분석에서 도출되는 판단

**1) 상위 4개가 모두 내부 요인이며, 모두 손실 규모가 "전체"입니다.**
화질 문제보다 시스템 안정성 문제가 우선입니다.

**2) 모션 블러는 7위입니다.**
체감상 가장 신경 쓰이는 항목이지만, 손실 단위가 프레임이고 다른 프레임으로 대체 가능합니다. 반면 상위 항목들은 발생 즉시 산책 하나를 통째로 잃습니다.

**3) 조도 변화(외1)가 화질 항목 중 최우선입니다.**
발생 빈도가 압도적이고, 손실 단위가 구간이라 프레임 선별로 보완되지 않으며, 클리핑은 복구 불가능합니다.

**4) 내7(관측 불가)이 1위인 이유**
자체 발생 빈도는 없습니다. 그러나 **다른 모든 실패의 손실을 증폭**시킵니다. 실패를 즉시 인지하면 산책 중 복구할 수 있지만, 인지하지 못하면 전량 손실로 확정됩니다.

**5) 내5(전원 불안정)의 가중치가 상승했습니다.**
내2가 내5에 종속되면서, 전원 안정화는 이제 **촬영 중단과 시각 오류를 동시에 막는 조치**가 되었습니다. 단일 조치로 두 항목을 해결하므로 투자 대비 효과가 가장 큽니다.

| **비가역** | **Zero W (촬영 단계)** | 내4~내9, 외1, 외5, 외6 |
| **부분 가역** | Zero W 기록 + 후단 복원 | **내2 (단조 시계 앵커링)**, 외2, 외4 |
| **가역** | Jetson / PC (후단) | 외3, 외7, 외8 |

> 내2는 "촬영 시 충분한 근거를 남겨두면 후단에서 복원 가능한" 유형입니다. Zero W가 해야 할 일은 정확한 시각을 확보하는 것이 아니라, **시각이 틀렸다는 사실과 복원에 필요한 기준값(단조 시계)을 함께 기록하는 것**입니다.

### 설계 원칙

1. **Zero W는 판단하지 않는다.** 연산 자원이 없고(내1), 촬영 시점에는 무엇이 좋은 프레임인지 알 수 없다.
2. **비가역 항목만 촬영 단계에서 방어한다.** 가역 항목에 자원을 쓰면 비가역 항목 방어가 무너진다.
3. **실패는 즉시 관측 가능해야 한다.** 인지되지 않은 실패는 전량 손실로 확정된다.
4. **복원 가능성을 남긴다.** 완벽하게 기록할 수 없다면, 최소한 사후 복원에 필요한 근거를 남긴다. 내2의 단조 시계 앵커링이 이 원칙의 사례다.

### 다른 하드웨어와의 결합

상시 전원 장치(Jetson Orin Nano)의 존재는 Zero W 단독으로는 해결할 수 없는 항목을 흡수합니다.

| 항목 | Zero W 단독 | Jetson 결합 |
|---|---|---|
| 시각 기준 (내2) | 불가 (RTC 없음) | **해결** — 로컬 NTP 서버 |
| 프레임 선별 (외7) | 불가 (연산 부족) | 해결 — 후단 처리 |
| 안정화·보정 (외2~외4) | 불가 | 해결 — 후단 처리 |
| 익명화 (외8) | 불가 | 해결 — 후단 처리 |

**시사점**: 새로운 페인 포인트를 만날 때, "Zero W에서 어떻게 해결할까"보다 **"이걸 상시 전원 장치로 넘길 수 있는가"** 를 먼저 검토하는 편이 효율적입니다. 넘길 수 없는 것만 Zero W가 책임집니다.

## 부록 — 검증 명령

각 페인 포인트의 현재 상태를 확인하는 명령입니다.

```bash
# 내2 — 시각 동기화 상태
timedatectl show -p NTPSynchronized --value
timedatectl status

# 내2 — Jetson NTP 서버와의 동기화 확인 (chrony 사용 시)
chronyc sources -v
chronyc tracking          # Last offset / RMS offset 확인

# 내2 — 단조 시계와 벽시계 동시 확인 (사후 보정 근거)
cat /proc/uptime          # 부팅 후 경과 초
date -Iseconds
cat /proc/sys/kernel/random/boot_id   # 재부팅 여부 판별용

# 내3 — 센서 모드 및 crop 확인
rpicam-hello --list-cameras

# 내5 — 전원 이상 여부 (0x0이 정상)
vcgencmd get_throttled
vcgencmd measure_volts

# 내9 — 저장 공간
df -h ~

# 외1/외2 — 실제 셔터 속도 확인 (촬영 중 메타데이터)
rpicam-vid -n -t 5000 --metadata - --metadata-format txt -o /dev/null | grep -i exposure

# 발열
vcgencmd measure_temp
```
