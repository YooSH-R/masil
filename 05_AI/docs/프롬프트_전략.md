# 산책 일지 / 이미지 생성 프롬프트 전략

`05_AI/Prompts/` 패키지는 AI 호출에 쓰이는 프롬프트(시스템 프롬프트, user 템플릿, 생성 파라미터, 응답 스키마)를 한 곳에 모아 관리하기 위한 **프롬프트 중앙 관리 패키지**다. 기존에는 `05_AI/prompts.py` 한 파일에 전부 들어 있었으나, 스테이지별로 파일을 쪼개 유지보수 단위를 분리했다 (`6db9308 ♻️ Refactor: Prompt Package Refactoring`).

> ⚠️ **현재 상태(2026-07-29 기준) 알아둘 것**
> 1. **`Prompts/` 패키지는 아직 실행 코드에 연결되어 있지 않다.** `Walk_Log/walk_log_pipeline.py`와 `Image_Generator/generate_flow_image.py`는 여전히 최상위 `05_AI/prompts.py`(리팩터링 이전 파일)를 `import prompts as P`로 가져다 쓴다. `Prompts/` 패키지를 참조하는 코드는 저장소 전체에서 아직 없다. 리팩터링 커밋도 기존 `prompts.py`를 지우지 않고 "무손실 분할" 형태로 병행 추가만 했다.
> 2. **패키지 초기화 파일명에 오타가 있다.** `Prompts/__init__,py`로, 마침표(`.`)가 아니라 쉼표(`,`)가 들어가 있다. 이 때문에 Python이 `Prompts/`를 패키지로 인식하지 못해 `from Prompts import PromptSpec` 같은 임포트가 `ImportError`로 실패한다 (`__init__.py`로 이름을 고쳐야 패키지가 동작한다).
>
> 즉 지금은 "다음 리팩터링 단계에서 쓸 설계도"에 가깝다. 아래 설명은 `Prompts/` 패키지 내부의 **의도된 구조와 각 파일의 역할**을 기준으로 정리했다.

## 1. 전체 파이프라인

3단계 체이닝 구조. Stage 1만 이미지를 보고(VLM), Stage 2·3은 Stage 1의 텍스트 기록만 본다(LLM).

```
프레임 이미지 1장
   │  Stage 1 (VLM, frame.py)         temperature=0.1
   ▼
구조화 관찰 기록 (JSON, 한국어)
   │  Stage 2 (LLM, diary.py)         temperature=0.8
   ▼                              │  Stage 3 (LLM, image.py)      temperature=0.6
자연어 산책 일지                    ▼
                              영어 이미지 생성 프롬프트 (+스타일)
                                   │  이미지 생성 모델
                                   ▼
                              삽화 / 스토리보드
```

- **Stage 1 (관찰 기록)**: 이미지 1장 → 구조화 JSON. 사실 위주로만 기록하고, 이후 단계는 이 JSON만 신뢰한다.
- **Stage 2 (일지 작성)**: JSON 배열 → 자연어 일지. 이미지를 보지 않으므로 "기록에 없는 것을 쓰지 않기"가 핵심 제약이다.
- **Stage 3 (이미지 프롬프트)**: JSON(한국어) → 이미지 생성 모델용 프롬프트(영어, 쉼표 나열 키워드). 실제 삽화 생성은 `Image_Generator/generate_flow_image.py`가 담당.

## 2. 패키지 구성과 파일별 역할

```
Prompts/
├── __init__,py   패키지 진입점 - export 목록, 이름→스펙 레지스트리 (파일명에 오타, 위 경고 참고)
├── spec.py       PromptSpec - 모든 프롬프트가 담기는 공통 "그릇"
├── vocab.py      관찰 기록 enum 어휘의 단일 정의 + 스키마 조각 생성 헬퍼
├── rules.py      스테이지 간 동기화가 필수인 공통 정책(개인정보) + 블록 합성 헬퍼
├── frame.py      Stage 1 - VLM 프레임 관찰 기록 프롬프트
├── diary.py      Stage 2 - 산책 일지 작성 프롬프트 (+ 문체 프리셋 4종)
└── image.py      Stage 3 - 이미지 생성 프롬프트 작성기 3종 (+ 스타일/네거티브 프리셋)
```

### 2.1 `spec.py` — `PromptSpec` (공통 그릇)

하나의 AI 호출에 필요한 것을 전부 담는 불변(frozen) dataclass.

```python
@dataclass(frozen=True)
class PromptSpec:
    user_template: str
    system: str | None = None
    temperature: float = 0.7
    max_output_tokens: int = 2048
    response_schema: dict | None = None
    examples: list[tuple[str, str]] = field(default_factory=list)

    def render(self, **kwargs) -> str: ...   # user_template.format(**kwargs)
    def tweak(self, **overrides) -> "PromptSpec": ...  # 일부 값만 바꾼 사본
```

- **왜 `temperature`를 프롬프트와 한 dataclass에 묶어 두는가**: 프롬프트 문구와 온도는 세트로 튜닝되는 값이기 때문이다 (관찰 추출=저온, 서술=고온). 따로 관리하면 같은 스테이지의 제어 지점이 두 곳으로 쪼개진다.
- `tweak()`으로 기존 스펙에서 온도만 바꾼 사본을 만들 수 있다. 예: `FRAME_EXTRACT.tweak(temperature=0.0)`.
- 이 파일은 표준 라이브러리 외 어떤 것도 import하지 않는다. 패키지 전체가 API 키 없이 단독으로 import/테스트 가능해야 한다는 제약(§3) 때문이다.

### 2.2 `vocab.py` — 관찰 기록 enum 어휘 단일 정의

Stage 1의 응답 스키마(`FRAME_SCHEMA`)와 시스템 프롬프트 안 `[형식 예시]` JSON, 이 두 곳에 흩어져 있던 enum 값을 한 곳으로 모은 파일.

- **존재 이유**: 분할 전에는 "공원|하천변|..." 같은 enum 값이 스키마와 예시 프롬프트 두 곳에 중복돼 있어, 값을 하나 추가할 때 한쪽만 고치면 어긋나는 문제가 있었다.
- 제공하는 어휘 목록: `LOCATION_TYPES`, `SURFACES`, `TIMES_OF_DAY`, `WEATHERS`, `SEASON_HINTS`, `PEOPLE_COUNTS`. 전부 공통 `UNKNOWN = "불명"`을 마지막 값으로 포함한다.
  - `PEOPLE_COUNTS`는 정확한 인원수 대신 구간(`없음/1/2~5/6~15/다수`)으로만 답하게 해 관찰 원칙 4번(개수는 구간으로 답한다)을 강제한다.
  - 리스트 순서는 모델에 제시되는 순서이자 약한 사전 확률이므로, 자주 등장하는 값을 앞에 두고 임의로 섞지 않는다.
- 스키마 조각 생성 헬퍼: `enum_field()`, `text_field()`, `array_field()` — 각각 enum 제약 문자열, 자유 서술 문자열, 문자열 배열 필드의 JSON 스키마 조각을 만든다. `frame.py`의 `FRAME_SCHEMA`는 이 헬퍼들로 조립된다.
- `options()`: 어휘 리스트를 `"공원|하천변|..."` 형태로 프롬프트 본문에 나열할 때 쓰는 유틸.
- 값을 추가할 때는 이 파일의 리스트만 고치면 `FRAME_SCHEMA`에 자동 반영된다. 단 `[형식 예시]` JSON은 손으로 유지하는 "예시"이므로 매번 갱신할 필요는 없다(예시에 없는 값이 나와도 정상).

### 2.3 `rules.py` — 스테이지 간 동기화가 필수인 공통 정책

여러 스테이지에 공통으로 들어가야 하는 "정책" 문구만 모아둔 파일. 무엇을 여기 두고 무엇을 각 파일에 남길지의 기준이 명확하다.

- **여기에 두는 것**: 스테이지가 달라져도 반드시 동일해야 하는 정책. 대표 사례가 개인정보 보호 — Stage 1이 상호명을 기록하지 않는데 Stage 3가 상호명을 언급하면 정책에 구멍이 생기므로, 문구를 한 곳에서만 관리한다.
- **여기에 두지 않는 것**: 스테이지마다 의도적으로 다르게 튜닝되는 "작성 지침"(예: "쉼표로 구분된 키워드로 출력"). 이런 규칙은 여러 파일에 비슷하게 중복돼 있어도 의도된 중복이다 — 목적은 중복 제거가 아니라 "동기화가 필요한 것만" 모으는 것.
- 제공하는 상수:
  - `PRIVACY_KO`: Stage 1(관찰 기록)용 전문. 애초에 기록 단계에서 남기지 않는 것이 가장 확실한 방어라는 관점.
  - `PRIVACY_KO_ONELINE`: Stage 2(일지) 작성 원칙 목록에 한 줄로 삽입되는 축약판. Stage 1이 이미 걸러주지만, 기록에 실수로 남았을 때의 2차 방어선.
  - `PRIVACY_EN`: Stage 3(이미지 프롬프트) 영어판. 번호 목록 안에 삽입되므로 둘째 줄 들여쓰기(3칸)를 유지해야 포맷이 깨지지 않는다.
- `join(*blocks)`: 여러 블록 문자열을 빈 줄 하나로 이어 붙이는 헬퍼. 시스템 프롬프트를 통짜 문자열 대신 이름 붙은 블록들의 합성으로 만들면, 블록 순서 변경/추가/제거가 한 줄짜리 편집이 된다. 각 블록의 앞뒤 공백은 벗겨내고, 블록 사이 개행 수는 이 함수가 보장한다. `frame.py`의 `FRAME_SYSTEM` 조립에 쓰인다.

### 2.4 `frame.py` — Stage 1: VLM 프레임 관찰 기록

이미지 1장을 보고 사람이 읽는 글이 아니라 **Stage 2/3이 소비할 구조화 데이터**를 뽑아내는 프롬프트. 목표는 "좋은 문장"이 아니라 "검증 가능한 사실".

- **시스템 프롬프트 블록 구성** (`rules.join()`으로 조립, 순서 고정):
  1. `_ROLE` — "산책 관찰 기록원" 역할 정의, 문학적 표현이 아니라 검증 가능한 관찰이 임무임을 명시.
  2. `_OBSERVATION_RULES` — 관찰 원칙 5가지: 보이는 것만 기록, 불확실하면 "불명", 사실과 추론 구분(+confidence), 개수는 구간으로, 방향 표현은 확실할 때만.
  3. `rules.PRIVACY_KO` — 개인정보 보호 정책 (§2.3).
  4. `_IMAGE_QUALITY` — 압축으로 화질이 낮을 수 있음을 안내, 뭉개진 대상은 추측 대신 "불명".
  5. `_OUTPUT_FORMAT` — JSON만 출력, 설명/인사말/코드펜스 금지.
  6. `_FORMAT_EXAMPLE` — 형식만 보여주는 예시 JSON. **이 블록에는 출력 예시용 중괄호 `{}`가 그대로 들어 있어 `.format()`을 쓰면 `KeyError`가 난다.** 변수를 넣어야 할 때는 항상 `<<NAME>>` 센티널 + `str.replace`만 사용한다.
  - 형식 지시(5, 6번)를 맨 끝에 두는 이유: 입력의 끝에 가까울수록 모델의 형식 준수율이 높기 때문이다.
- **`FRAME_SCHEMA`**: 응답 JSON 스키마. `vocab.py`의 헬퍼로 조립되며, `scene`/`notable` 등 자유 서술, `location_type`/`weather` 등 enum, `animals`/`objects` 등 배열, `confidence`(시간대·날씨·장소유형에 대한 신뢰도 점수), `unreadable`(판별 불가 플래그) 필드를 갖는다. 항목을 추가/삭제하려면 이 스키마와 `_FORMAT_EXAMPLE`을 함께 손봐야 한다.
- **`FRAME_EXTRACT`** (최종 `PromptSpec`):
  - `system`은 위에서 조립한 `FRAME_SYSTEM`.
  - `user_template`은 프레임별로 바뀌는 값(세그먼트, 경과 시간, 촬영 일시, 위치)만 담고, 마지막 두 줄에서 관찰 원칙과 겹치는 지시를 한 번 더 반복한다. **의도된 중복**이다 — 이미지 바로 뒤(입력의 끝)에 오는 지시가 형식 준수율이 가장 높기 때문. 촬영 일시가 주어지면 그 값을 `time_of_day`보다 우선하고 confidence를 1.0으로 고정하라는 지시도 여기 있다.
  - `temperature=0.1` — 환각 억제 목적. 온도를 올리면 없는 사물이 등장한다.
  - `max_output_tokens=2048` — thinking 모델이 사고 토큰을 먼저 소모하므로 넉넉하게 잡음.
  - `response_schema=FRAME_SCHEMA`.
  - **Stage 1에는 few-shot(`examples`)을 쓰지 않는다.** 이미지 없는 텍스트 예시 턴을 앞에 붙이면 VLM이 "이미지를 보지 않고도 JSON을 쓸 수 있다"고 학습해 환각이 늘어나기 때문. 형식 학습은 시스템 프롬프트 안의 `[형식 예시]` 블록이 대신한다.
  - system/user 분리 기준: system은 모든 프레임에 공통이라 프레임 수만큼 곱해지지 않는 불변 규칙, user는 프레임마다 바뀌는 값과 이미지(Gemini는 `contents`가 필수 필드이고 이미지도 user 턴의 parts에 담기므로 자동화 파이프라인이어도 생략 불가).

### 2.5 `diary.py` — Stage 2: 산책 일지 작성 (+ 문체 프리셋)

이미지를 보지 않고 Stage 1이 남긴 JSON 기록만으로 일지를 쓴다. 핵심 제약은 "기록에 없는 것을 쓰지 않기".

- `_DIARY_SYSTEM_TEMPLATE`: 작성 원칙 6가지(기록에 없는 시간/감정/대화 금지, 반복 서술 대신 장면 전환 기준 문단 분리, confidence<0.5는 완화/생략, unreadable 프레임 무시, 모순되면 다수결 또는 변화로 해석, 개인정보 정책) + `<<STYLE>>`/`<<PRIVACY>>` 센티널 + 출력 형식(한 줄 요약 → 본문 → 코스/날씨/오늘 만난 것 메타 정보). 이 템플릿에도 출력 형식 예시용 중괄호(`{날짜}`)가 있어 `.format()` 대신 센티널 치환을 쓴다.
- `DIARY_STYLES`: 문체 프리셋 딕셔너리. `[문체]` 블록을 통째로 대체하며 서로 다른 프리셋의 지시를 상속하지 않는다.
  - `plain` (기본값): 1인칭 과거형, 담담하고 따뜻한 톤, 과장된 수사·이모지 없음, 본문 300~500자.
  - `emotional`: 혼잣말하듯 짧은 문장, 기록에 있는 요소로만 감각(빛·소리·공기) 묘사, 본문 200~350자.
  - `workout`: 개조식 3~5줄, 코스/노면/환경 조건 위주, 감상 표현 최소화.
  - `pet`: 반려견을 주인공으로 서술, `animals`에 반려견이 없는 프레임에서는 억지로 등장시키지 않음, 본문 250~400자.
  - 새 문체를 추가하려면 이 딕셔너리에 항목만 넣으면 된다.
- `diary_spec(style=DEFAULT_DIARY_STYLE)`: 등록되지 않은 문체면 `KeyError`. 선택된 문체와 `rules.PRIVACY_KO_ONELINE`을 시스템 템플릿에 채워 `PromptSpec`을 만든다. `temperature=0.8`(문장의 자연스러움 목적, 밋밋하면 0.9~1.0까지 올려도 됨), `max_output_tokens=2048`.
- `_DIARY_USER_TEMPLATE`: 산책 개요(날짜/총 소요/프레임 수) + 시간순 JSON 라인 목록을 받아 "위 기록으로 산책 일지를 작성해라"로 마무리.

### 2.6 `image.py` — Stage 3: 이미지 생성 프롬프트 작성 + 스타일 조립

관찰 기록(한국어) → 이미지 생성 모델용 프롬프트(영어)로 번역·재구성하는 단계. 대부분의 이미지 생성 모델이 영어 프롬프트, 그중에서도 쉼표로 나열된 키워드 구조에 더 잘 반응하기 때문이다.

**작성기(writer)가 3개인 이유**: 소비하는 입력 범위와 요구되는 제약이 서로 다르다.

| 작성기 | 입력 범위 | 출력 | 핵심 차별점 |
|---|---|---|---|
| `IMAGE_PROMPT_WRITER` | 프레임 전체 기록 중 하나의 대표 장면 | 영어 키워드 시퀀스 | 기본 삽화용, 한 장면을 한 장으로 |
| `FLOW_IMAGE_WRITER` | 산책 전체(여러 프레임, 시간순) | 영어 키워드 시퀀스 | "여러 장소를 하나로 합치지 말라"는 추가 제약 필요 — 안 그러면 서로 다른 장소가 뒤섞인 불가능한 풍경이 나온다. 넓은 가로 구도(길이 이어지는 인상) 선호 지시 포함 |
| `PANEL_CAPTION_WRITER` | 장면 하나의 기록 | 한국어 12자 이내 명사구 | 스토리보드 각 칸에 붙는 초단문 캡션 |

세 작성기의 규칙 목록은 서로 겹치지만(쉼표 나열 출력, 60단어 제한 등), 스테이지별로 독립적으로 튜닝될 수 있는 성질이라 각자 전문을 들고 있다. 동기화가 필수인 개인정보 조항(`rules.PRIVACY_EN`)만 `rules.py`에서 가져와 공유한다.

- `IMAGE_PROMPT_WRITER` / `FLOW_IMAGE_WRITER` 공통 규칙: 기록에 있는 요소만 사용(랜드마크·사물 창작 금지), 쉼표로 구분된 키워드 시퀀스로 출력(주제/장면→환경→시간대→날씨→계절→분위기→구도 순), 개인정보 정책 준수(식별 가능한 인물·얼굴·로고·상표·번호판 금지, 사람은 먼 실루엣으로만), 60단어 이내, 스타일/품질 키워드는 별도로 붙이므로 여기서 넣지 않음, 설명·따옴표·마크다운 없이 프롬프트만 출력. `temperature=0.6`, `max_output_tokens=512`.
- `PANEL_CAPTION_WRITER`: 기록에 있는 요소만으로 12자 이내 명사구 캡션 하나만 출력, 문장부호·설명·따옴표 없음, 상호명·사람 외모 금지. `temperature=0.4`, `max_output_tokens=64`.

**스타일/조립**

- `IMAGE_STYLES`: 5종 프리셋 — `watercolor`(기본값, 수채화), `storybook`(동화책 삽화), `lineart`(잉크 라인아트), `photoreal`(사실적 사진), `pixel`(16비트 픽셀아트). 각 값은 영어 스타일 키워드 문자열이며, 추가하려면 딕셔너리에 항목만 넣으면 된다.
- `IMAGE_NEGATIVE`: 공통 네거티브 프롬프트 리스트(텍스트/워터마크/서명/로고/상표/번호판/식별 가능한 얼굴/초상/왜곡된 신체/과채도/난잡함/저해상도/JPEG 아티팩트 제거).
- `IMAGE_SUFFIX`: 최종 조립 시 항상 붙는 공통 접미어(`"no text, no watermark"`).
- `build_image_prompt(scene_prompt, style=DEFAULT_IMAGE_STYLE, extra="")`: 장면 프롬프트에 스타일과 접미어를 이어 붙여 `{"prompt": ..., "negative_prompt": ...}` dict를 만든다. 등록되지 않은 스타일이면 `KeyError`. 조립 순서는 **장면 프롬프트 → 스타일 → (선택)추가 문구 → 공통 접미어**. 반환 dict는 특정 이미지 API에 종속되지 않는 형태이므로, 호출부가 각 API의 실제 필드명(`prompt`/`negative_prompt` 등)에 매핑해서 쓴다.

### 2.7 `__init__,py` — 패키지 진입점 (파일명 오타 있음, 위 경고 참고)

패키지 바깥에서 이름으로 스펙을 꺼내 쓰기 위한 얇은 조립 계층.

- 하위 모듈(`rules`, `vocab`, `diary`, `frame`, `image`, `spec`)에서 필요한 심볼을 가져와 재노출하고 `__all__`에 등록한다.
- **프롬프트를 추가할 때 반드시 손대야 할 세 곳**: import 줄 / `__all__` / `_FACTORIES`. 하나라도 빠뜨리면 에러 없이 그냥 안 보이게 되므로, 이 파일 docstring은 "`__all__` 존재 검사 테스트를 함께 두라"고 명시한다.
- `_FACTORIES`: 이름(`str`) → 스펙을 만드는 `Callable`의 딕셔너리. 인자가 없는 스펙(`frame_extract`, `image_prompt_writer` 등)은 `lambda: SPEC`으로, 인자를 받는 `diary_spec`처럼 호출 시점에 값이 결정되는 스펙은 함수 자체를 등록한다.
- `get(name, **kwargs)`: 이름으로 스펙을 얻는 공개 API. 예: `get("diary", style="emotional")`. 등록되지 않은 이름이면 사용 가능한 이름 목록을 포함한 `KeyError`.
- `REGISTRY`: `_FACTORIES`를 즉시 호출해 만든 `dict[str, PromptSpec]`. 분할 전 `prompts.py`의 `REGISTRY`와 호환되는 dict를 제공하기 위한 것으로, **새 코드는 `get()`을 쓰고 참조가 없는 것이 확인되면 이 변수는 제거 대상**이라고 명시돼 있다.

## 3. 패키지 전역 불변 규칙 (`__init__,py` docstring 발췌)

1. 이 패키지는 외부 의존이 없다. `requests`, `cv2`, `config` 등을 import하지 않는다 — API 키 없이 import되고 테스트되어야 한다.
2. 변수 치환 방식은 두 가지뿐이며 섞지 않는다.
   - `system`: `<<NAME>>` 센티널 + `str.replace` (출력 예시용 중괄호가 들어 있으므로 `.format()` 사용 불가)
   - `user_template`: `str.format`
3. 동기화가 필수인 문구(개인정보 정책)는 `rules.py`에, enum 값은 `vocab.py`에 둔다. 그 외의 중복은 의도적으로 허용한다 — 스테이지별로 따로 튜닝되기 때문이다.

## 4. 실행 로직과의 관계 (실제 호출부)

`Prompts/` 패키지 자체는 프롬프트 "내용"만 들고 있고, API 호출·이미지 압축·파일 I/O 같은 실행 로직은 두지 않는다. 실행은 다음 두 스크립트가 담당한다 (단, §서두의 경고대로 **현재는 `Prompts/` 패키지가 아니라 최상위 `prompts.py`를 가져다 쓴다**):

- `Walk_Log/walk_log_pipeline.py`: 프레임 → 관찰 기록(Stage 1) → 산책 일지(Stage 2) → (선택) 이미지 프롬프트(Stage 3)까지의 전체 파이프라인. `--style`로 문체, `--image-prompt`/`--image-style`로 삽화 프롬프트 생성 여부와 스타일을 지정.
- `Image_Generator/generate_flow_image.py`: 관찰 기록 → 장면 선정(로컬) → 이미지 프롬프트 작성(LLM) → 삽화 생성(이미지 모델) → 스토리보드 합성(로컬)까지 담당. `IMAGE_PROMPT_WRITER`/`FLOW_IMAGE_WRITER`/`PANEL_CAPTION_WRITER`/`IMAGE_STYLES`/`IMAGE_NEGATIVE`/`build_image_prompt`가 없으면 즉시 에러를 낸다(내장 대체 프롬프트를 두지 않아 관리 지점이 쪼개지는 것을 막기 위함).

`Prompts/` 패키지를 실제로 쓰려면 두 스크립트의 `import prompts as P`를 `from Prompts import ...` 또는 `import Prompts as P`로 바꿔야 하며, 그 전에 `__init__,py` → `__init__.py` 파일명부터 고쳐야 패키지로 인식된다.

## 6. 튜닝 체크리스트

1. **환각이 보이면** → `frame.py`의 `temperature`를 0.0으로 낮추거나, 관찰 원칙 1번을 user 파트 끝에 한 번 더 반복하는 패턴을 강화한다.
2. **"불명"이 너무 많으면** → 프롬프트 문제가 아니라 이미지 해상도(긴 변 768px 확보) 문제일 가능성이 높다.
3. **형식이 깨지면** → `response_schema`(`FRAME_SCHEMA`)가 실제로 API에 전달되는지 먼저 확인한다. 그래도 흔들리면 few-shot(`examples`)을 검토하되, Stage 1(VLM)에는 붙이지 않는다.
4. **일지가 밋밋하면** → `diary.py`의 `temperature`만 0.9~1.0으로. `frame.py`(Stage 1)는 절대 올리지 않는다.
5. **프레임이 너무 많으면** → `generate_flow_image.py`의 장면 선정 로직(인접 프레임의 `location_type`/`weather`/`time_of_day`/`objects` 유사도 기반 전환 감지)으로 대표 장면만 추려 Stage 2/3에 넣는다.
6. **enum 값을 추가/변경하면** → `vocab.py`의 리스트만 고친다. `FRAME_SCHEMA`는 자동 반영되지만 `frame.py`의 `[형식 예시]` JSON은 손으로 유지되는 예시이므로 필수 갱신 대상은 아니다.
7. **문체/이미지 스타일을 추가하면** → 각각 `diary.py`의 `DIARY_STYLES` / `image.py`의 `IMAGE_STYLES` 딕셔너리에 항목만 추가한다.
8. **새 프롬프트(스펙)를 패키지에 추가하면** → `__init__,py`의 import 줄 / `__all__` / `_FACTORIES` 세 곳을 모두 갱신해야 한다. 하나라도 빠뜨리면 에러 없이 조용히 누락된다.
